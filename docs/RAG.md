# RAG 链路：设计、评测与规模基准

> 本文回答三个问题：**链路每一步在做什么、为什么这么选**；**凭什么说它是对的**（评测与消融）；
> **1200 篇时还撑不撑得住**（规模基准）。所有数字都能用仓库里的脚本一条命令复现。

---

## 1. 链路总览

```
loader ──► chunker ──► index ──► retriever ──► rerank ──► package
 清洗      内容寻址分块   增量索引     RRF 混合召回    可插拔重排    引用打包
 front       + 标题前缀    + 对账     + 无答案判定    + 预算回退    + chunk_id
 matter                                  + 多样性
```

| 阶段 | 代码 | 关键决策 |
|---|---|---|
| 加载清洗 | `src/app/rag/loader.py` | front matter 声明部门/品类/季节/平台/生效期/版本；**权威度 `authority` + 按小节归属的可比较事实 `key_facts`** |
| 分块 | `src/app/rag/chunker.py` | 按标题切段 → 320 字滑窗/60 重叠；表格逐行成块；**chunk_id 内容寻址**；正文带 `《标题》> 小节` 前缀 |
| 索引 | `src/app/rag/index.py` | sha256 + `chunker_version` 增量；块 id 差集更新；写向量库前先 `delete_doc`；按文档指纹对账 |
| 召回 | `src/app/rag/hybrid.py`、`bm25.py` | BM25 字段加权（标题 2.0 / 小节 1.5 / 正文 1.0）+ 倒排索引；向量余弦；**RRF 融合**；无答案判定；同文档配额 + MMR |
| 冲突裁决 | `src/app/rag/conflict.py`、`src/app/common/conflicts.py` | 同一口径多份规定 → 按权威度阶梯取一条（单位/百分比先归一）；**不丢命中**，只标 `is_primary`；文档内部矛盾单独报 |
| 重排 | `src/app/rag/rerank.py` | `none / heuristic / llm / cross` 可插拔；`RAG_RERANK_TIMEOUT_MS` 预算；超时/失败回退融合序并标 `rerank_degraded` |
| 统一入口 | `src/app/rag/pipeline.py` | `/api/rag/search` 与对话工具 `search_knowledge` **共用一条链路 + 一份缓存**；响应带 `conflicts` / `conflict_check` |
| 子图 | `src/app/rag/skill.py` | LangGraph 子图：rewrite → search → package（批量巡检用） |

## 2. 三个关键设计：融合、无答案判定与重排

这三条决定检索结果**是否可信**，而不只是精度微调。

### 2.1 融合：RRF 而非 min-max 加权

向量分与 BM25 分属于不同量纲（余弦相似度 vs 词法得分），加权前必须先归一化。而逐查询
min-max 归一化会把最高分恒定为 1.0、最低恒定为 0.0 —— 无论文档多不相关，第一条命中都接近满分，
系统永远不会返回"没找到"。对一个要给运营做决策的 Agent 来说，这比"少召回一条"严重得多。

因此融合采用 **RRF**（`score = Σ 1/(60 + rank_i)`）：只看名次、不看分数量纲，天然免疫标定问题。

### 2.2 无答案：RRF 回答不了"有没有答案"

RRF 是名次信号：哪怕全库都是垃圾，也总有一个块排第 1。所以另加**绝对**判据：

```
如果 最像块的余弦相似度 < 0.25  且  查询词覆盖率 < 0.25  且  BM25 最高分 < 15（词法证据不强）
    → hits = []，no_answer = true
```

阈值不是拍的：用 20 条**应该弃答**的负样本（`data/eval/rag_negatives.jsonl`）与 38 条正样本标定，
当前语料上的实测边界是「正样本最低 vec=0.276 / 负样本最高 vec=0.236」。
换 embedding 或语料大改后必须重跑 `eval_rag --negatives` 重新标定——脚本会打印
`no_answer_rate` 与"该弃答却硬答"的清单，改了没重标定会立刻暴露。

### 2.3 重排：独立阶段 + 四后端选型

重排是链路里的第二阶段，不是 `sorted()` 的别名：四后端、候选上限、超时预算、失败回退，
并且**回退会打标**（`rerank_degraded`），一路传到 `citations` 与 `run_detail`——用户看到的"排过序"必须是真排过序。

**量纲对齐**：启发式重排把词覆盖分叠加到融合分（RRF，~1e-2 量级）之前，先把融合分归一化到 [0,1] 再加权，
否则词覆盖会盖过融合名次（调优时的一组对照：未归一化会让 R@1 从 89.5% 掉到 68.4%，据此定型），让启发式只做同量级的 tie-breaker；
MMR 里的相关度同理（见 `hybrid._diversify` 注释）。

### 2.4 口径冲突：两份制度都召回时，谁说了算

问「女装清仓触发天数是几天」，通用《清仓 SOP》写「可售天数 ≥ 60 天」，女装部门细则写「≥ 45 天」。
两份都在库里、都会被召回。没有这一层时，模型的典型行为是**折中**（"大约 50 天"）或把两个都念一遍——
用户拿到的口径**在任何一份制度里都不存在**。

#### 2.4.0 先定边界：部门面是"可比性闸门"，不是"排序权重"

权威度阶梯（政策 > 部门 > 通用 > 案例）只回答"**同一适用面内**谁优先"，它回答不了"这条规则适不适用"。
把两者混在一起就会出现这类错误（复审实测）：

```
管理员问「男装清仓触发条件」→ 男装细则没声明该口径
  → 裁决退化成「女装 45 天 vs 通用 60 天」→ 女装胜出 → 男装问题被答成 45 天
```

所以先定规则，再谈实现：

| 编号 | 规则 | 说明 |
|---|---|---|
| **C1 可比性** | 只有 `A(doc)` 与问题适用面 `Q` 相交的事实才进入裁决；部门面：`doc.department ∈ Q.dept ∪ {通用, 全部}` | 不相交 = 并行规则，没有"谁压过谁" |
| **C1-补充 多部门面 / 比较意图** | `\|Q.dept\| > 1` **或问句是跨部门比较意图**（只认**部门语义**词：`哪个部门/哪些部门/各部门/跨部门/部门之间/各线`…）时**不做跨部门排序**：通用/governance 作基线，各部门细则按"若为 X 部门则为 Y"逐条给出；没声明口径的部门写明"按通用执行"（`uncovered_departments`） | 比较类问题没有唯一答案，单方胜出 = 答错一半；通用比较词（区别/对比/分别/相比）不算部门比较，否则"清仓和补货的区别"也会被塞"只按 X 部门作答" |
| **C2 部门面缺失** | `Q.dept` 为空 → 只有 `通用/governance` 参与裁决；部门文档降级为**部门例外**（`department_overrides`），只能写成"若问的是 X 部门则 Y" | 通用问题的答案不能被某个部门的细则替换 |
| **C3 部门账号** | 部门账号的 `Q.dept = 账号部门`；问句指向他部门时分两种：**完全不可见**（`问句面 ∩ 可见面 = ∅`）只按通用口径作答并给 `scope_notice`；**部分可见**（交集非空但缺一部分，如"女装和男装…"）在比较句里同样**不做单方裁决**，可见部门口径降级为 `department_overrides`，notice 点名缺失部门 | 不越权、不臆造，而且要说清"哪一半看不到" |
| **C4 权威度阶梯** | 在**可比集合内**排序：`governance > dept > general > case` | 原有阶梯，作用域变小 |
| **C5 平级次序** | 版本号（按数字比）> 生效开始日 > `doc_id`（确定性） | 可复现 |
| **C6 取值归一** | 单位别名 + 百分比↔小数互认（仅 (0,1)） | 避免"60天 vs 60日"这种假冲突 |
| **C7 同值不冲突** | 归一后相等不报（跨部门同值也算一致） |  |
| **C8 文档内部矛盾** | `kind=intra_doc`：只报"语料需修订"，**不裁决** | 加载期已 WARNING |
| **C9 生效期** | 只考虑 `as_of` 有效文档 | 检索侧已过滤 |
| **C10 检测与收敛分离** | 池内检测（落败方常在 6~20 名）+ top-k/触发词相关性 + 排除词（只认用户原话） | 两轮复审踩出来的 |
| **C11 不确定不裁决** | 无可比口径 → `unavailable`；只有单一来源 → `none` + `single_source_keys` | 诚实状态 |
| **C12 不丢召回** | 裁决只标 `is_primary`，不删命中 | 丢文档 = 召回事故 |
| **C13 消费契约** | 提示词：`cross_doc` 只用 winner；`intra_doc` 不作答；`department_overrides` 只作补充句；`none/unavailable` 不得暗示已核对 |  |
| **C14 可观测** | 计数 `ok/none/unavailable/intra/suppressed/skipped/overrides/scope_mismatch/scope_partial/comparison/multi_department` + 语料覆盖率（`docs_without_facts`、**`department_gaps`**：哪个部门一篇都没声明口径） | 失败模式几乎都是静默；部门例外缺一块的根因也能看到 |
| **C15 判定顺序** | **部门面过滤 → 相关性收敛 → 取值归一 → 权威度裁决 → 状态** | 先排序后过滤正是"男装被女装压过"的来源 |

大概率情形（规则 → 期望）：

| 情形 | 期望 |
|---|---|
| 部门账号问本部门 / admin 问女装、童装 | 45 天（dept 胜通用；童装归女装） |
| **admin 问男装** | **60 天（通用）**，绝不出现 45 天 |
| **admin 问无部门面** | **60 天（通用）** + 例外句"若为女装部门则为 45 天" |
| 两个部门都有口径、无通用口径 | 不裁决；两者都是 `department_overrides`，状态 `none/unavailable` |
| 跨部门同值 | 不算冲突 |
| 部门账号问他人部门 | **只按通用口径作答** + `scope_notice`「可见范围内没有 X 部门的口径」（不给本部门口径） |
| 部门账号问"本部门 + 他部门"（部分可见） | **比较句不单方胜出**：通用基线 + 可见部门例外（`department_overrides`）+ notice 点名缺失部门 |
| 多部门比较（"男装和女装的…"） | **不产生跨部门胜出**：通用基线 + 各部门"若为 X 部门则 Y"（`department_overrides`）+ `scope_notice` |
| 跨部门比较意图（"哪个部门/各部门/跨部门比较"，未点名部门） | **同样不裁决**：只按可见部门 + 通用口径作答，`scope_notice` 明确"不要据此断言各部门一样"；未声明口径的部门写"按通用执行"（`uncovered_departments`）；**通用比较词（"清仓和补货的区别""两个供应商交期对比"）不算跨部门比较，按普通问题作答** |

实现落点：`src/app/rag/facets.py`（部门面识别与适用性判断，唯一实现）、`rag/conflict.py`（C15 顺序）、
`security/scope.py::kb_department_filter(user, departments)`（管理员按问题部门收敛）。

做法（`src/app/rag/conflict.py` + `src/app/common/conflicts.py`）：

1. 文档在 front matter 声明**可比较事实**、**权威度**与（可选的）**触发词**，事实可以按**小节**归属：

   ```yaml
   authority: dept                       # governance / dept / general / case
   key_facts: 触发条件|clearance_trigger_days=45天; *|clearance_min_discount=6折
   fact_triggers: clearance_trigger_days=触发,门槛,判断标准,清仓什么时候,清仓开始!补货,订货,采购,折扣,物流,退货
   ```

   - `小节|key=value`：只在该小节的块上生效（**单向匹配**：声明名必须出现在真实标题里，
     声明「触发条件」可命中「触发条件（女装）」；拼错成「触发条件X」不命中任何标题，
     加载时会 WARNING——双向匹配会让拼写错误静默通过）；
   - `*|key=value` 或省略前缀：全文档生效（旧语料默认行为）；
   - 为什么要按小节收敛（复审 P2-2）：文档级事实会挂到每个块上，于是问「清仓怎么执行」
     命中的是"执行节奏"小节，却也会触发「触发天数」冲突，提示词就要求模型先解释一个
     用户没问的阈值。按小节收敛后，冲突只在相关小节被召回时出现；
   - `fact_triggers`：**补召回**通道。事实按小节收敛后，换一种说法（"清仓天数门槛"）
     可能召回不到事实所在的小节，冲突就静默消失；问句命中触发词时该口径照样参与比对。
     **三条规矩**（都是被误报打出来的）：
     1. **口径词优先**：`触发/门槛/天数门槛/预警/阈值`，不要用裸词 `天数`（会把
        「补货的目标覆盖天数」也拽进来）；
     2. **时间/意图词必须带对象**：`清仓什么时候`、`清仓开始` —— 裸 `什么时候` 无法区分
        "清仓什么时候开始"（该报）和"清仓什么时候补货"（不该报）；
     3. **必须配排除词**：`!补货,订货,采购,折扣,物流,退货`。排除词优先，命中即判不相关
        （回落到结构化相关性）。排除词**只看用户原话**——`清仓` 的同义词含"折扣清仓"，
        拿改写结果判排除词会把几乎所有清仓问题误杀（实测检出率 7/8 → 4/8）。

2. 同一 `key` 出现多个**不同**取值 → 一次冲突，按阶梯裁决：
   **中台治理口径 > 部门细则 > 通用规则 > 历史案例**；
   同权威度再比版本号（`v1.10 > v1.9`，按数字不比字符串）→ 生效日期 → doc id（可复现）。
   取值比较前先做归一（复审 P1-3）：单位别名（`天/日`、`小时/h`、`％/%`）与"百分比 ↔ 小数"
   （`15%` 与 `0.15` 视为同一阈值，仅限 (0,1) 区间，避免把「0.5 折」当成 50%）——
   不归一就会造出假冲突，输出"采用 60 天…不采用 60 日"这种自相矛盾的提示。
3. **在候选池上检测，在 top-k 上收敛**（这是两次复审踩出来的平衡）：
   - 只比 top-k → 落败片段排在第 6~20 名时冲突整条丢失（早期版本只检出 3/8 条这类问法）；
   - 池内全报 → 问「分批节奏」也会被塞进「触发天数」冲突（噪声）；
   - 现在：`detect(pool, top_hits=top-k, query=...)`，口径**相关**的判据是
     「top-k 片段带该口径」**或**「问句命中该口径的触发词」。当前题集（25 道冲突题）通过率见 `--conflicts`；
     两条噪声问法（分批节奏、补货覆盖天数）仍被抑制。
   - 胜出片段常常不在 top-k：`conflicts[*].winner.snippet` 带原文，`## 冲突提示` 里会附上，
     模型才有依据可引（数值本身在工具 JSON 里，grounding 不会误判成编造）。
4. **不丢文档**：召回结果保持原样，只给命中打 `is_primary`，并把 `## 冲突提示` 单独交给提示词
   （丢掉落败文档会让"女装细则"在女装问题上消失——那是召回事故，不是冲突治理）。
5. **诚实状态**：`conflict_check ∈ {ok, none, unavailable}`，语义写死在 `detect()` 与提示词里：
   - `unavailable` = **没做比对**（召回片段没有相关可比口径）。不得暗示"已核对"；
   - `none` = 比对了相关口径、**在本次召回范围内**没有分歧；`conflict_diagnostics.single_source_keys`
     非空时说明这些口径只有一份来源（无法交叉验证）；
   - `ok` = 有冲突，按 `conflict_note` 取一条。
6. **文档内部不一致单独报**（复审 P2-1）：同一份文档对同一口径写了两个取值，是**语料缺陷**
   而不是"谁压过谁"。这类条目 `kind=intra_doc`，只进"语料内部不一致"提示，
   **不给采用结论**；加载期已对重复声明打 WARNING（运行时这条分支是防御性保留）。
7. **可观测**：`/api/health.rag_conflicts`（checked/ok/none/unavailable/intra/suppressed）、
   `/api/health.rag_facts`（多少文档/事实声明了口径、几个小节名写错）、
   `/api/metrics.rag.conflicts`。这套机制的失败模式几乎都是"静默"，没有计数只能靠猜。

演示语料里有两处真实冲突，可直接复现：

| 口径 | 通用/规则 | 部门/案例 | 胜出 | 理由 |
|---|---|---|---|---|
| `clearance_trigger_days` | 60 天（清仓 SOP · v1.2） | 45 天（女装细则 · v0.9） | 45 天 | 部门细则优先于通用规则（**版本低也照样赢**） |
| `broken_size_alert_days` | 7 天（断码补全 SOP · v1.2） | 5 天（历史案例） | 7 天 | 现行规则优先于历史案例 |

已知边界（如实写在这里，不藏在代码注释里）：

- **没有触发词、且事实所在小节没被召回时不会报冲突**——这是"宁少报不误报"的取舍，
  所以新增口径时要同时配 `fact_triggers`，并在 `data/eval/rag_conflicts.jsonl` 加同义问法变体；
- 冲突检测依赖**召回广度**（池大小 = `RAG_RERANK_MAX_CANDIDATES`，默认 30）与
  `key_facts` 的覆盖率（当前 14 篇里 6 篇声明，9 条事实）；没覆盖的口径永远不会报冲突；
- **排除词只作用于触发词通道**：用户已经在看这一节（top-k 带该口径）时，排除词不会把冲突压掉
  ——那是"用户确实在问这一节"，不该被关键词屏蔽；
- 触发词是关键词匹配，天然有边界：`换季的判断标准和清仓一样吗` 这类"在问标准"的问法仍会报
  （可接受）；而 `清仓什么时候补货`、`清仓折扣什么时候结束` 这类"意图在别处"的问法已被排除词挡住，
  并有 `expect_no_conflict` 负例守着；
- **部门面靠词表识别**（男装/男式/男士/女装/女式/女士/童装/儿童…）：识别不到就按"无部门面"处理
  （通用口径 + 部门例外），**不会**给出错误部门的裁决；新增部门/别名时要同步 `rag/facets.py` 的
  `DEPARTMENT_WORDS` 与 `data/eval/rag_conflicts.jsonl` 的 admin×部门题；
- 品类/季节/仓/平台面已作为 `Claim` 的适用面字段保留，但本轮只做部门面裁决；扩展到这些维度时
  按 C1 的方式在 `facets.claim_applicable()` 里加条件，不要在生产路径上另写一套。

```bash
python scripts/eval_rag.py --conflicts      # 25 道冲突题：检出、胜出口径、状态诚实性、无关问题不误报、问法变体、过触发负例、admin×部门面、部门账号问他人部门、部分可见、多部门比较、跨部门比较意图、非部门比较负例（"清仓和补货的区别"等不误判为跨部门比较）
```

### 2.5 知识库回答也要能溯源（否则出口闸门会误杀）

出口溯源校验（`src/app/agents/grounding.py`）原来只认取数结果 id `res_xxx`，而且工具结果
在 `run_detail` 里统一截 500 字。于是 SOP 第 3、4 段的阈值被截断后，**有出处的回答被判成编造**，
用户看到"⚠️ 自检未通过"——闸门自己制造了噪音。

两处修正：

- `chunk_id`（`doc_id#sha1[:8]`）成为合法来源，与 `res_xxx` 并列；编造的 chunk_id 照样会被抓；
- 知识库结果按 `KB_EVIDENCE_MAX_CHARS`（默认 6000）保留，普通详单工具仍截 500 字。

另外「本轮调用了几个工具」不再只数取数登记（`steps`）——知识库检索不进取数登记，
只认 `steps` 会把"按 SOP 回答"判成"本轮未调用任何工具"，`tool_call_count()` 现在把
`tool_trace` 里的调用也算上。回归用例见 `tests/test_grounding_kb.py`。

## 3. 评测：一条命令复现

```bash
python scripts/eval_rag.py --negatives          # 正负样本 + 无答案命中率
python scripts/eval_rag.py --ablation           # 消融对照表（bm25/vector/rrf/rerank）
python scripts/eval_rag.py --conflicts          # 口径冲突题集（权威度裁决是否挑对）
python scripts/eval_rag.py --min-recall 0.8                       # CI 门槛（比的是 Recall@5）
python scripts/eval_rag.py --negatives --min-no-answer 0.85       # 弃答率门槛（需带 --negatives 才有值）
python scripts/bench_rag_scale.py --docs 1200   # 1200 篇规模基准
```

### 3.1 消融（38 正样本 + 20 负样本，同一题集）

| 融合 | 重排 | R@1 | R@5 | MRR | 无答案 | 说明 |
|---|---|---|---|---|---|---|
| bm25 | none | 92.1% | 100% | 0.961 | 90% | 只用关键词 |
| vector | none | 94.7% | 100% | 0.974 | 90% | 只用哈希向量 |
| **rrf** | **none** | **100%** | **100%** | **1.000** | **90%** | 两路名次融合 |
| rrf | heuristic | 100% | 100% | 1.000 | 90% | 微调，不改变顺序 |
| rrf | llm | 100% | 100% | 1.000 | 90% | 离线环境全部超时 → 回退（表中"降级"列会显示次数） |

结论：**RRF 优于任一单路**（+5~8 个点 R@1），这就是把 0.6/0.4 加权换掉的理由。
`llm` 行在离线跑等于 `rrf`，因为重排超时后回退——表格里的"降级"计数就是防止把这种情况误读成"LLM 没用"。

> 注意：38 条题集是**回归闸门**，不是质量声明。它的作用是"改坏了能立刻发现"，
> 真实规模下的表现要看下面的规模基准（1200 篇合成语料）。

### 3.2 规模基准（1200 篇 / 4457 块，`bench_rag_scale.py --docs 1200 --query 40`）

> 语料构成：约 **40% 变体**（以 `data/kb` 的 14 篇真实 SOP 为模板，改 `doc_id` / `department` / `season` / `version`，正文模板相同）
> + 约 **60% 合成干扰文档**（不同品类/规模的运营资料，不承载业务规则），模拟真实库里大量无关资料。
> 因此该基准同时覆盖「近重复标题的区分能力」与「噪声稀释下的召回质量」。

| 指标 | 实测（`data/eval/scale-1200.json`，一次运行） | 目标 |
|---|---|---|
| 索引构建 | 29.1 s（冷机/占满 CPU 时更慢） | < 60 s |
| 检索器装载 + BM25 建索引 | 1.1 s | — |
| 向量内存（512 维 float32） | ≈ 9 MB（4457 块） | — |
| **单查询 P50 / P95** | **45.9 ms / 69.4 ms** | P95 < 250 ms |
| R@1 / R@5 | **97.4% / 100%**（40% 变体 + 60% 干扰文档） | R@1 ≥ 85% |
| 无答案命中率 | 85%（14 篇真实语料时为 90%） | — |

> 数字与机器负载/合成语料种子有关，改动检索或冲突检测后请重跑同一条命令对比；
> 冲突检测在候选池上只多一次 30 条命中的事实解析；合成语料继承真实 SOP 的 front matter（含 `key_facts`），
> 所以这一项在规模基准里确实参与计算，其开销已包含在上表数字中。

达成规模目标的两个关键改动：

1. **BM25 换倒排索引**：`rank_bm25` 的 `get_scores` 是纯 Python 全量循环，5700 块时单次 200ms+；
   改成 `token → (docs, tf)` 倒排（numpy 存储）后只对**命中词**的文档打分。同机改造前后对比 P95 428 ms → 82 ms。
2. **向量分改矩阵乘**：向量已 L2 归一化，`Q @ D.T` 直接是余弦；逐行调 `cosine()` 是 500ms+ 的来源。
   这一项先把同机 P95 从 605 ms 降到 428 ms。

R@1 在 1200 篇（含 60% 干扰文档）为 97.4%（真实语料 14 篇时为 100%）：干扰文档会稀释词法信号，但 RRF 融合的两路名次仍然把正确文档顶到前面；哈希向量没有语义能力，所以口语化问法仍要靠真实 embedding 提升。
生产要把 `EMBEDDING_BACKEND=tencent`（或本地 BGE）+ `VECTOR_STORE=qdrant` 打开，
再用 `eval_rag.py --mode vector`（或 `--rerank llm/cross`）对照验证收益——线上也可以直接用 `GET /api/rag/search?backend=<none|heuristic|llm|cross>` 做 A/B。这才是"用数据说话"，而不是"听起来更高级"。

## 4. 四件事必须诚实地做

1. **降级要打标**：重排超时、向量库失败、embedding 失败，都要在 `citations` / `run_detail` /
   `/api/metrics.rag` 里显式标注。用户看到的"排过序"必须是真排过序。
2. **无答案优先于凑答案**：宁返回空结果 + "知识库没有相关内容"，也不塞 5 条不相关 SOP 让模型编。
3. **冲突要解，不许折中**：同一口径多份规定时按权威度取一条，并把"取了哪条、为什么"写进回答；
   没填 `key_facts` 就说"冲突检查不可用"，不能默认"没冲突"。
4. **阈值是标定出来的，会漂**：阈值写在 `src/app/config.py`，注释里带实测边界，
   并由 `eval_rag --negatives` 持续看住。任何"我调大了一点"的改动都必须跑一遍脚本。

## 5. 可选组件与生产配置

| 组件 | 默认 | 生产建议 | 说明 |
|---|---|---|---|
| 向量 | 本地 512 维哈希 n-gram | `EMBEDDING_BACKEND=tencent`（TokenHub，1024 维）或自建 BGE | 哈希向量只有词法信号，与 BM25 高度重叠 |
| 向量库 | `VECTOR_STORE=memory`（numpy 暴力余弦） | `VECTOR_STORE=qdrant` | 千级语料内存模式够用；万级以上要 ANN |
| 重排 | `RAG_RERANK_BACKEND=heuristic` | `llm`（DeepSeek listwise）或 `cross`（BGE-reranker） | 超时预算默认 400 ms，超时回退融合序 |
| 索引对账 | 启动时按文档指纹对账 | 同 | `RAG_INDEX_RECONCILE=false` 可关闭 |
| 知识库证据预算 | `KB_EVIDENCE_MAX_CHARS=6000` | 同 | 进溯源校验时单条知识库结果保留多少字（普通工具仍 500 字） |

环境变量完整清单见 [CONFIG.md](CONFIG.md)。
